# 2026.330.1834 — fix(chrome-cdp): restart a SUPERVISED browser through its owner

## Summary

Two defects in the helper scripts this candy installs, both replicated on the KDE-over-VNC pod
(opencharly/opencharly#1294), where Chrome is an init-system program on the Plasma socket and
`chrome-restart` / `browser-open` are the advertised restart and URL-open paths.

- **`chrome-restart` raced the supervisor.** It killed Chrome and relaunched it itself (`pkill`,
  two fixed sleeps, `swaymsg exec chrome-wrapper`). In a pod that SUPERVISES Chrome the supervisor
  also restarts it, so the manual path raced it into TWO browsers on one `--user-data-dir` — a
  collision the wrapper's Singleton-lock cleanup hides rather than reports — and the launch it
  performed belonged to the compositor's socket, not the session the pod shows.
- **`browser-open` had the same gap** in its on-demand launch.

**The fix is additive.** Both helpers take a branch BEFORE any launch and any kill: when the init
config carries `[program:chrome]`, restart THAT (`supervisorctl restart chrome` — the one owner
waits for the old process and starts the new one, so no sleep is needed and no second browser can
exist); otherwise `browser-open` delegates the same way. The branch is decided from the CONFIG, not
the control socket, so a user the supervisor refuses gets a loud `supervisorctl` failure instead of
a silent duplicate.

Everything below that branch — the `pkill`/wait/`swaymsg` compositor path — is BYTE-IDENTICAL to
before, so no non-supervised (compositor-launched) pod changes. That path is deliberately not this
change's subject: the pod this work exists for supervises its browser.

The candy's plan gains two build-scope checks: each helper carries the supervised branch (the
`program:chrome` probe and the supervisor restart). A `.gitignore` is added at the same time so a
local `python3 -m py_compile cdp-proxy` (the repo's ONE Python helper; `browser-open` is Node and
`chrome-restart` is POSIX shell) cannot leak `__pycache__` into a commit — that is how the first
attempt committed a `.pyc`.

### Spike

Two restart mechanisms, BOTH exercised on the real pod (a disposable `check-kde-vnc-cdp-pod` run
with the alternative as a probe step beside the shipped one):

```
# (a) ask the init system that owns the browser (CHOSEN) — synchronous and reported
  PASS  check chrome-restart restarts the SUPERVISED browser and CDP answers again  [bed-chrome-restart]  exit=0
  PASS  check after the restart the browser is RUNNING under the supervisor         [bed-chrome-restart-live]  RUNNING
  PASS  check the browser is maximized AGAIN after the restart                      [bed-maxok-after-restart]  MAXOK
  PASS  check browser-open brings the STOPPED supervised browser back and opens the URL  [bed-browser-open-supervised]  exit=0
  (run 2026.330.1541, exit 0)

# (b) kill the browser outright and let supervisord's autorestart bring it back — ALSO WORKS
  PASS  check SPIKE: kill Chrome outright and let supervisord do the restarting        [bed-spike-pkill]  exit=0
  PASS  check SPIKE: the supervisor's autorestart brings the killed browser back on its own  [bed-spike-autorestart]  (attempts=2, elapsed=5.342s)  exit=0
  PASS  check SPIKE: and CDP answers again after that autorestart                      [bed-spike-autorestart-cdp]  CDP: ok (127.0.0.1:39727)
  (run 2026.330.1802, exit 0 — the probe steps are removed from the shipped bed)
```

Both work. (a) wins on three stated grounds, not on taste: it is SYNCHRONOUS (it returns only after
the supervisor has stopped and started the program, so a caller can act on the result), it reports a
failure (a refused control socket is an error, where a signal-only restart is silent), and it does
not depend on `autorestart` being enabled for a CLEAN exit — (b) would do nothing for a pod whose
service sets `autorestart: unexpected`, and it cannot distinguish "restarted" from "already running".
(b) is held as the fallback if a supervisor control socket is ever unreachable from a caller's user;
this run shows it is reachable (a) succeeded.
